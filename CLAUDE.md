# SVES Connect: project conventions

Single app: React 19 + Vite (`src/`) and Express 5 + MySQL via `mysql2` (`server/`). Deployed to cPanel/WHM (Setup Node.js App). See DEPLOY.md.

## Module rules (keep development unmixed)
- One module = one route prefix, one UI folder `src/modules/<key>/`, one API folder `server/modules/<key>/` mounted at `/api/<key>`.
- Register every module in `src/core/modules.js`. Unbuilt modules render `ModulePlaceholder` with their planned scope.
- Modules never import from each other; shared code goes in `src/ui` (components), `src/core` (auth, api) or `server/core`.
- No new npm packages without approval. Auth uses Node crypto (scrypt + HS256 JWT), not bcrypt/jsonwebtoken.
- Schema: `server/db/schema.sql` (idempotent); run with `npm run migrate`. No Mongo/Mongoose.

## Design system (derived from the Vishnu logo)
- All colors/spacing/radius/shadows/gradients are CSS variables in `src/styles/tokens.css`. Never hardcode colors in components.
- Palette: primary purple `#A1248D`, secondary orange `#C2570C` (buttons) / `#F08327` (graphics only), accent lime `#A8CC3C` (decoration; text `#4D7C0F`), ink `#2A0F36`, bg `#FBF8FC`, text `#1F1F1F`, muted `#5B5568`. All text pairs meet WCAG AA.
- Max 2-3 brand colors per screen: purple + orange; lime only for status/small highlights.
- Fonts: Plus Jakarta Sans (headings), Inter (body).
- Components live in `src/ui/index.jsx` (Button, Card, Input, Select, Field, Modal, Table, Badge, Navbar, Sidebar, ToastProvider/useToast, Loader, Skeleton, EmptyState). Use them; add new shared ones there.
- Motion 150-250ms; respect prefers-reduced-motion. Forms show inline validation messages.
- Logo: the ORIGINAL Vishnu logo `public/logo.jpg` (from reference/svecw_logo.jpg; never redraw or alter it; favicon `public/favicon.png`). Site name: "SVES Connect", organisation "Sri Vishnu Educational Society".

## Status
- Done: events module, design system, shell/layouts, home, MySQL auth, AI assistant (`/assistant`), college account hierarchy.
- Accounts: one login table; login asks College + email + password. Hierarchy admin > principal (one default account per college, official emails listed in `server/core/org.js`, e.g. principal@svecw.edu.in for VWU) > HOD (email, department) > lab coordinator (role `lab_incharge`; email, department, lab name). Each level creates/edits (email, name, lab name; HOD department rename cascades to labs/equipment/events)/resets/disables only the level below, inside its own college (HOD: own department). Default password `svesconnect@123` (env DEFAULT_PASSWORD) (not forced to change: `must_change_password` is kept but always 0). No public sign-up.
- Per-college routes: UI `/c/<code>/hods|labs|lab|principal`, API `/api/c/<code>/users`; one implementation (`server/modules/org`, `src/modules/org`) reused by every college. Colleges are seeded by `npm run migrate` from `server/core/org.js` (add a college there, re-run migrate).
- Lab Equipment (Module 1, in `server/modules/labs` + `src/modules/labs`): data is organised college > department > lab (`labs` table; one lab per coordinator, created with the coordinator). Labs are never merged: every list/page is per lab. Every question is OPTIONAL (only the equipment name, given at creation, is needed); uploads are optional too. Registration form = `server/modules/labs/formSpec.js` (single source of truth: base sections from the SVES template PDF + 14 department templates + "general"; served at `/api/public/form-spec`; UI asks one question at a time and honours `showIf` / `highValue` (> ₹1.5 lakh)). To add/change a question, edit formSpec.js only. Workflow: draft > submitted > approved | rejected (with note). The HOD of the lab's department gives the FINAL approval (publishes); there is no Principal approval step (`verified` is a legacy state that migrate converts to approved). The Principal, and admin, can view every lab and record, department-wise or lab-wise (`/c/<code>/lab-details`), but cannot approve. Only `approved` is public (`/explore`), and public views never include finance, warranty/AMC, known issues or internal documents (allow-list in labs/routes.js). Uploads are optional, stored in STORAGE_DIR (default ./storage, git-ignored) as base64 JSON, max 8 MB, PDF/image/Word/Excel. The AI assistant ingests approved equipment only.
- Passwords: every account starts with the shared default password. ONLY college administrators (role `college_admin`) are forced to change it at first sign-in (`must_change_password=1`; migrate flags any still on the default; `/api/admin/*` and `/api/c/*` answer 403 until changed). Everyone else is never forced and may use the optional Change password link. A password set/reset by the central admin or anyone else does NOT force a change. Forgotten passwords: central admin sets passwords for principals, HODs and college admins of every college; HODs/principals/college admins reset the level below. The login page has an optional "Change password" link (college + email + current password + new one) -> `POST /api/auth/change-password-login`; signed-in users can also use Change password in the sidebar. Admin Unlock/Set password handles forgotten passwords.
- Equipment entry (current form, ALL new equipment; designed with the user step by step, change it only after discussing): lab in-charge enters everything, HOD approves, Principal/admin view. "Add equipment" asks name (type-ahead of the college's shared catalogue `equipment_catalog`; picking/typing an existing name fills Type and Purpose and says it already exists), Type (simple category list `CATEGORIES` in formSpec.js, keys `cat_*`, one list for engineering/polytechnic/pharmacy/dental/science), short Purpose; the same name may be added again in one lab for a different configuration (optional "Configuration" text, `data.variant`, shown next to the name; public summaries still add all units of that name together). Then the PAGE-STYLE form (`EquipmentFlow.jsx`: one page per category with ALL its fields visible at once, two-column grid, step chips on top to jump anywhere, side panel with live unit/condition card and tips, sticky Back/Next bar; a category over ~10 field-weights continues on a second page; the last page holds the review and Send to HOD) with sections in `CURRENT_SECTIONS` (formSpec.js): Basic (purpose, brand, model, quantity, condition = counts needing repair / not in use, working is derived, year bought, warranty years, ONE photo), Purchase (total cost in rupees, vendor, funding, invoice + invoice upload; internal), Technical (feature/value table + spec file), Service (AMC; internal), Operation & safety (manual/SOP uploads; internal), How it is used (courses, projects, hours/week; public), Other documents. Every question has help + example, every step a help box, answers autosave ~1 s after typing ("All changes saved"), the form opens at the first page that has an empty field, friendly plain-language errors only. `derive()` in labs/routes.js fills quantity/units_working/current_status/equipment_cost_lakhs. Old records keep their old template keys and old 80-question spec (buildSpec by key) and still work.
- Approval and publishing (current design): `equipment.status` is the workflow of the WORKING copy (`data`): draft > submitted > approved | rejected; `equipment.pub_data` is the last APPROVED copy and is what every public page, public count, summary and public search reads (published = `pub_data IS NOT NULL`). The in-charge may add equipment and edit at any time; editing an approved/submitted item sets it back to draft but the public keeps the approved version until the HOD approves. The HOD reviews per lab (`/c/<code>/lab-details/:labId/review`): sees every equipment with all details and edit history (`equipment_history`, edits merged per person per 30 min), can edit any field (`/c/<code>/lab-details/equipment/:id/edit`, same flow as the in-charge), send an item back with a note, then ONE "Approve lab and publish" (`POST /labs/:id/approve`) publishes everything submitted; a HOD edit of an approved item also waits for the next lab approval. Deleting a published equipment is not allowed for the in-charge.
- Internal reports for HOD (own department) / Principal / admin, print to PDF only (no CSV/Excel by the user's choice): `/c/<code>/report/labs` (every lab with its equipment, includes cost) and `/c/<code>/report/equipment` (search/type, e.g. "server": every unit in the college grouped by equipment with lab, department, location, units, working, make/model, year, cost). Finance appears only in these internal views, never public.
- Public view (`/explore/c/<code>/equipment`, `/equipment/<slug>`): equipment-wise for the whole college (grouped by normalised name; `server/modules/labs/summary.js`): exact unit counts, working units, units per department, brands, courses, main specs, the labs that have it. The wording summary is written by Groq from PUBLIC facts only (cached in `equipment_summaries`, rebuilt when facts change; template text without a key). Public never gets finance, vendor, warranty, service or any uploaded document; only the equipment photo is public (`PUBLIC_FILE_KINDS`). Lab record pages for printing/Save as PDF (browser print, no PDF library): public `/explore/lab/:id/record` (public info + photos) and internal `/c/<code>/lab/record` (in-charge) or `/c/<code>/lab-details/:labId/record` (HOD/Principal/admin; includes purchase and service details).
- Dashboards module (`server/modules/dashboards`, `src/modules/dashboards`, route `/c/<code>/dashboard`, API `/api/c/<code>/insights/*`): the landing page of the Principal and HODs (HOD = own department only; admin opens any college as Principal). Tiles, charts (`src/ui/Charts.jsx`, plain SVG/CSS, no library), alerts, an ask-anything box and a filter panel, a result table with totals, and PDF by browser print (only the result, or a full report with chosen sections; cost can be switched off). The AI NEVER touches the database: Groq (or a keyword reader without a key) only turns the sentence into a structured request (`ask.js`), `engine.normalize()` whitelists it, and `engine.js` computes exact rows from the college's data; the written summary may only use numbers from the result. Entities: equipment, labs, incharges (faculty-wise = lab in-charges), departments, hods, events; filters: department, lab, type, equipment, condition (working/repair/not_in_use/not_working), status, year/month/from/to (equipment: date added; events: event date), boughtFrom/boughtTo, free text; group by department/lab/type/equipment/in-charge/year/month. To add research / projects later: register a new entity in `ENTITIES` (engine.js), add it to the `SCHEMA` text and keyword rules in ask.js, and give it tiles/charts in `dashboard()`.
- Dialogs: never use the browser's alert/confirm/prompt. Use `useDialog()` from `src/ui` (`confirm({title,message,confirmText,tone:'question'|'danger'|'warning'}) -> bool`, `info/success/warning/error(message,title)`, `show({tone,title,message,details,buttons})`). `useToast()` error and warning messages automatically open a dialog (only success notices stay as quiet toasts); `core/api.js` turns network failures into a plain-language message. Forms use `Modal`: a WIDE centred dialog (780px; `size="sm"` 500px for short messages/credentials, `size="lg"` 1040px) whose dark backdrop itself scrolls (fixed, overflow-y:auto, panel `margin:auto`), so it is never cut off and has no inner scroll box; forms inside are laid out in two columns (one in sm / on phones) with the button row sticky at the bottom. Do not give the dialog a fixed height, `dvh`/`vh` max-height or its own scroll area, and do not make it a narrow drawer (users complained about both).
- Search module (`server/modules/search`, `src/modules/search`): ONE index over departments, labs and equipment (records submitted or approved; finance is never indexed). Same approach as the original assistant (local MiniLM embeddings + cosine, answer from Groq) but scoped by who asks: public = approved only; HOD = own department; Principal = own college; coordinator = own lab; admin = all. If the embedding library cannot load (no sharp binary on the cPanel server) or DISABLE_EMBEDDINGS=1 it silently uses keyword ranking; if GROK_API_KEY is unset the assistant answers with the closest matches + source links. Index rebuilds a moment after any lab/equipment change (`search.touch()`); `/api/chatbot/ingest` forces a rebuild. UI: `/search` page, SearchBox on /explore and on the Principal/HOD "Labs & equipment" page, assistant with Mine/All-published toggle and source links.
- Common information: `/api/c/<code>/overview` (HOD/Principal/admin) = per-department totals (labs, published, awaiting, working, investment, high-value) shown above the lab list. Public pages: /explore > college > department (`/explore/c/<code>/d/<dept>`) > lab > equipment, each lab kept separate.
- Events module (`server/modules/events`, `src/modules/events`): generic for ANY event/project type (BAJA, workshop, fest, consultancy ...); `typeSpec.js` only gives starting folders + filename hints, folders/sub-folders are otherwise free. Data: `events`, `event_files` (folder, subfolder, title, description, contributor/credit, date, tags, is_public, machine summary, extracted text); files on disk under `STORAGE/events/<COLLEGE>/<year>/<id>-<event>/<folder>/<subfolder>/`. One login table: roles `event_coordinator` and `event_member` carry `users.event_id` and land on `/c/<code>/event/<id>`. HOD/Principal/admin create an event (+ coordinator login) at `/c/<code>/events`; coordinator uploads with metadata and adds team members; everyone on the event can view/download every file; HOD (or Principal/admin) publishes. Public (`/events`, `/events/:id`, no login): published events grouped by college, auto-made summary (description + extractive highlights from PDF/docx/pptx/xlsx/txt text, no AI key needed) and only files flagged public. Uploads are base64 JSON, max 8 MB. The old BAJA browser prototype (`svecw-main`) was removed from the app; its data is brought in with `npm run import:baja -- <backup.json>` (see DEPLOY.md).
- College administrators (role `college_admin`, one per college, seeded by migrate as `admin@<principal's domain>`, VWU = admin@vwu.edu.in, default password): full administrator rights INSIDE their own college only. `collegeContext` (server/core/college.js) maps the role to `admin` for `/api/c/<own college>/*` (so every existing admin power works: approve, edit, delete, events, files, reports, dashboard) and blocks every other college (403); `/api/admin/*` accepts `college_admin` but scopes every query/create/update/delete to `req.scopeCollege` (own college, never central admins; cannot create central admins; can create principals, HODs, coordinators, event people and other college admins; set/reset passwords, disable, delete, edit incl. HOD department and lab name via `org.updateAccount`). Frontend: `RequireAuth` treats `college_admin` as `admin`; `/admin` shows a scoped console with a "How the public sees your college" card. Logins listed in `docs/college_admin_logins.md`.
- Administrator console (`server/modules/admin`, `src/modules/admin`, route `/admin`, API `/api/admin/*`, admin only): overview of every college (accounts, labs, equipment, events, files, with links into each college's labs/events/principal pages), Accounts (list/filter all users; create ANY role in ANY college incl. event coordinators/members and extra admins; unlock = enable + default password + forced change; set a password; edit name/email; disable/enable; delete, never self or the last admin), all labs, all events (publish/unpublish). Admin logs in with college "SVES Central Administration". Inside any `/c/<code>/...` page the admin acts like the Principal and can also approve/reject submitted equipment, delete equipment, manage events and files. Lab coordinators/HODs keep their own lab/department scope.
