# SVES Connect: project conventions

Single app: React 19 + Vite (`src/`) and Express 5 + MySQL via `mysql2` (`server/`). Deployed to cPanel/WHM (Setup Node.js App). See DEPLOY.md.

## Module rules (keep development unmixed)
- One module = one route prefix, one UI folder `src/modules/<key>/`, one API folder `server/modules/<key>/` mounted at `/api/<key>`.
- Register every module in `src/core/modules.js`. Unbuilt modules render `ModulePlaceholder` with their planned scope.
- Modules never import from each other; shared code goes in `src/ui` (components), `src/core` (auth, api) or `server/core`.
- No new npm packages without approval. Auth uses Node crypto (scrypt + HS256 JWT), not bcrypt/jsonwebtoken.
- Schema: `server/db/schema.sql` (idempotent); run with `npm run migrate`. No Mongo/Mongoose.

## Design system (derived from the Vishnu logo)
- All colors/spacing/radius/shadows/gradients are CSS variables in `src/styles/tokens.css`. Never hardcode colors in components.
- Palette: primary purple `#A1248D`, secondary orange `#C2570C` (buttons) / `#F08327` (graphics only), accent lime `#A8CC3C` (decoration; text `#4D7C0F`), ink `#2A0F36`, bg `#FBF8FC`, text `#1F1F1F`, muted `#5B5568`. All text pairs meet WCAG AA.
- Max 2-3 brand colors per screen: purple + orange; lime only for status/small highlights.
- Fonts: Plus Jakarta Sans (headings), Inter (body).
- Components live in `src/ui/index.jsx` (Button, Card, Input, Select, Field, Modal, Table, Badge, Navbar, Sidebar, ToastProvider/useToast, Loader, Skeleton, EmptyState). Use them; add new shared ones there.
- Motion 150-250ms; respect prefers-reduced-motion. Forms show inline validation messages.
- Logo: the ORIGINAL Vishnu logo `public/logo.jpg` (from reference/svecw_logo.jpg; never redraw or alter it; favicon `public/favicon.png`). Site name: "SVES Connect", organisation "Sri Vishnu Educational Society".

## Status
- Done: events module, design system, shell/layouts, home, MySQL auth, AI assistant (`/assistant`), college account hierarchy.
- Accounts: one login table; login asks College + email + password. Hierarchy admin > principal (one default account per college, official emails listed in `server/core/org.js`, e.g. principal@svecw.edu.in for VWU) > HOD (email, department) > lab coordinator (role `lab_incharge`; email, department, lab name). Each level creates/edits (email, name, lab name; HOD department rename cascades to labs/equipment/events)/resets/disables only the level below, inside its own college (HOD: own department). Default password `svesconnect@123` (env DEFAULT_PASSWORD) (not forced to change: `must_change_password` is kept but always 0). No public sign-up.
- Per-college routes: UI `/c/<code>/hods|labs|lab|principal`, API `/api/c/<code>/users`; one implementation (`server/modules/org`, `src/modules/org`) reused by every college. Colleges are seeded by `npm run migrate` from `server/core/org.js` (add a college there, re-run migrate).
- Lab Equipment (Module 1, in `server/modules/labs` + `src/modules/labs`): data is organised college > department > lab (`labs` table; one lab per coordinator, created with the coordinator). Labs are never merged: every list/page is per lab. Every question is OPTIONAL (only the equipment name, given at creation, is needed); uploads are optional too. Registration form = `server/modules/labs/formSpec.js` (single source of truth: base sections from the SVES template PDF + 14 department templates + "general"; served at `/api/public/form-spec`; UI asks one question at a time and honours `showIf` / `highValue` (> ₹1.5 lakh)). To add/change a question, edit formSpec.js only. Workflow: draft > submitted > approved | rejected (with note). The HOD of the lab's department gives the FINAL approval (publishes); there is no Principal approval step (`verified` is a legacy state that migrate converts to approved). The Principal, and admin, can view every lab and record, department-wise or lab-wise (`/c/<code>/lab-details`), but cannot approve. Only `approved` is public (`/explore`), and public views never include finance, warranty/AMC, known issues or internal documents (allow-list in labs/routes.js). Uploads are optional, stored in STORAGE_DIR (default ./storage, git-ignored) as base64 JSON, max 8 MB, PDF/image/Word/Excel. The AI assistant ingests approved equipment only.
- Passwords: every account starts with the shared default password and nobody is prompted to change it. The login page has an optional "Change password" link (college + email + current password + new one) -> `POST /api/auth/change-password-login`; signed-in users can also use Change password in the sidebar. Admin Unlock/Set password handles forgotten passwords.
- Equipment catalogue (table `equipment_catalog`, one shared list per college; `GET /api/c/<code>/catalog?q=` type-ahead): "Add equipment" asks ONLY for the name (type-ahead of names already used in the college, matched on any word) and the purpose. Picking a suggestion fills in its purpose; an unknown name is added to the catalogue for every lab (spelling is reused from the catalogue; purpose is stored as the equipment description). New equipment is created as a draft with the "general" template and no longer jumps into the long form; details are added later via Continue. Further fields/categories are to be designed with the user.
- Search module (`server/modules/search`, `src/modules/search`): ONE index over departments, labs and equipment (records submitted or approved; finance is never indexed). Same approach as the original assistant (local MiniLM embeddings + cosine, answer from Groq) but scoped by who asks: public = approved only; HOD = own department; Principal = own college; coordinator = own lab; admin = all. If the embedding library cannot load (no sharp binary on the cPanel server) or DISABLE_EMBEDDINGS=1 it silently uses keyword ranking; if GROK_API_KEY is unset the assistant answers with the closest matches + source links. Index rebuilds a moment after any lab/equipment change (`search.touch()`); `/api/chatbot/ingest` forces a rebuild. UI: `/search` page, SearchBox on /explore and on the Principal/HOD "Labs & equipment" page, assistant with Mine/All-published toggle and source links.
- Common information: `/api/c/<code>/overview` (HOD/Principal/admin) = per-department totals (labs, published, awaiting, working, investment, high-value) shown above the lab list. Public pages: /explore > college > department (`/explore/c/<code>/d/<dept>`) > lab > equipment, each lab kept separate.
- Events module (`server/modules/events`, `src/modules/events`): generic for ANY event/project type (BAJA, workshop, fest, consultancy ...); `typeSpec.js` only gives starting folders + filename hints, folders/sub-folders are otherwise free. Data: `events`, `event_files` (folder, subfolder, title, description, contributor/credit, date, tags, is_public, machine summary, extracted text); files on disk under `STORAGE/events/<COLLEGE>/<year>/<id>-<event>/<folder>/<subfolder>/`. One login table: roles `event_coordinator` and `event_member` carry `users.event_id` and land on `/c/<code>/event/<id>`. HOD/Principal/admin create an event (+ coordinator login) at `/c/<code>/events`; coordinator uploads with metadata and adds team members; everyone on the event can view/download every file; HOD (or Principal/admin) publishes. Public (`/events`, `/events/:id`, no login): published events grouped by college, auto-made summary (description + extractive highlights from PDF/docx/pptx/xlsx/txt text, no AI key needed) and only files flagged public. Uploads are base64 JSON, max 8 MB. The old BAJA browser prototype (`svecw-main`) was removed from the app; its data is brought in with `npm run import:baja -- <backup.json>` (see DEPLOY.md).
- Administrator console (`server/modules/admin`, `src/modules/admin`, route `/admin`, API `/api/admin/*`, admin only): overview of every college (accounts, labs, equipment, events, files, with links into each college's labs/events/principal pages), Accounts (list/filter all users; create ANY role in ANY college incl. event coordinators/members and extra admins; unlock = enable + default password + forced change; set a password; edit name/email; disable/enable; delete, never self or the last admin), all labs, all events (publish/unpublish). Admin logs in with college "SVES Central Administration". Inside any `/c/<code>/...` page the admin acts like the Principal and can also approve/reject submitted equipment, delete equipment, manage events and files. Lab coordinators/HODs keep their own lab/department scope.
